1. AGREED PROCESS

Employee initiator submits/resubmits -> current direct line manager recommends
approval or rejection -> HR verifies -> Management approves or rejects.

Return destinations:
  Line manager -> employee initiator.
  HR -> employee initiator.
  Management -> HR. HR can resolve the issue and verify again for Management,
                or return the request to the employee initiator.

A manager's rejection recommendation is advisory; it does not reject the request.
A Management return clears the HR verification and retains the manager's
recommendation. A return to the initiator clears current recommendations and
verification. Resubmission starts a new review round and retains prior history.
Material changes or a changed reporting line cannot reuse outdated reviews.

2. COVERAGE

The shared Approval Centre at /hr/approvals handles these 22 request types:

  Attendance and time:
    TIME_CREDIT              Site-travel time credit
    TIME_CREDIT_REVOCATION   Revocation of an approved time credit
    LEAVE                    Leave request
    OVERTIME                 Overtime request
    TIMESHEET                Timesheet approval
    SHIFT_SWAP               Shift-swap request

  Financial and recruitment:

    REQUISITION              Recruitment requisition
    OFFER                    Offer authorization before sending

  Performance, assessment and employment:
    GOAL                     Employee goal
    PERFORMANCE              Performance review finalization
    ASSESSMENT_RELEASE       Release of an acknowledged practical assessment
    DEVELOPMENT              Development-plan approval
    JOB_DESCRIPTION          Job-description proposal approval
    CATEGORY_CONVERSION      Employee-category/code conversion
    NOTICE_CHANGE            Separation notice change
    SEPARATION_WITHDRAWAL    Withdrawal after separation approval
    SETTLEMENT               Final settlement before payroll handoff

The main separation workflow retains its existing native policy, evidence,
authority and workstream controls. Its return routing follows the same agreed
process. Assessment practical review, moderation, acknowledgment, JD owner review,
clearances and financial preparation remain prerequisites, rather than substitutes
for the business approval chain.

Employee identity in the new public commands and review records uses employee
codes. Internal numeric foreign keys stay within the backend. The owner is the
subject employee for personal requests; requisitions, payroll runs and offers
use their initiating/requesting/processing employee. A valid company, linked
employee account and current reporting line are required. This implementation
does not invent proxy authority for an unavailable or deceased employee.

3. USER EXPERIENCE AND FINAL EFFECTS

The centre provides My requests, reviewer queue, audit view, request-type filter,
source details, immutable review history, stage-specific actions, reasons and a
deliberate review confirmation. It requires a single active company. HR can select
a leave policy during verification. The UI supports desktop and mobile layouts.

Legacy decision buttons route to the centre. Direct legacy approval/rejection
API calls fail with HR-4201 before changing balances, payments or source status.
Existing save/submission entry points preserve their native result shape while
submission enters the common chain. Old payroll/overtime approval matrices do
not authorize new decisions through the retired decision paths.

Only a Management decision applies immediate native effects: leave balance and
attendance updates, overtime roster updates, claim status, loan activation or
write-off, timesheet/swap/goal/requisition status, payroll-run approval, current
attendance rule effects, and performance finalization. Final effects and approval
history commit together or roll back together. Creating a loan or time credit
no longer activates it automatically. Payslip approval/disbursement requires an
approved parent payroll run and the existing financial separation of duties.

Specialist actions remain explicit after approval: assessment release,
development/JD execution, category conversion, notice change, offer sending,
separation withdrawal and settlement handoff. Each native action verifies the
matching final decision and exact source revision inside its own transaction,
then records execution as APPLIED with its native effects. SEPARATE_ACTION in the
centre means that the authorized specialist action is still required. The native
domain's prerequisites and role permissions still apply.

Employees can withdraw their pending leave, overtime, claim or shift-swap requests
at any active review stage. This records WITHDRAWN and clears the queue, preserving
the audit. It is distinct from a Management rejection and does not cancel an
already approved business effect.

4. AUTHORIZATION, INTEGRITY AND INTERFACES

Five typed MCP tools have matching POST /api/hr/approvals/<route> endpoints:
  hr_approval_list     list
  hr_approval_read     read
  hr_approval_preview  preview
  hr_approval_submit   submit
  hr_approval_action   action

Commands use strict shared schemas, employee codes, source references, expected
versions, mandatory reasons and UUID idempotency keys. Caller-supplied company,
actor, role, employee row ID or return destination is rejected. Stale commands
return 412. Replays recheck current access and cannot repeat business effects.

Authorization uses the verified account's linked employee and company. Manager
actions require the current direct manager. Initiator, manager, HR verifier and
Management decision maker are distinct actors for a request. General admin
permissions do not implicitly grant final approval.

The three approval tables have forced tenant RLS. Audit and replay receipts are
immutable; source snapshots and replay payloads use existing C4 encryption.
Transactions lock the approval and source records. Reviewed parent fields and
claim/time/payroll lines cannot be edited after approval. Child-line edits lock
the approval parent, preventing concurrent finalization from approving old facts.
Source fingerprints include material child records and assessment revisions.

Each transition writes an outbox event transactionally. No new email/SMS delivery
consumer is claimed by this implementation; live delivery depends on the existing
event infrastructure and configured consumers.
