# Attendance capture and reviewed history import

This release follows the attendance setup releases migration. Deploy backend and frontend together. No production data is changed by the development work.

## Operating workflow

1. HR registers each physical serial under Capture operations, selecting its IANA timezone and stale threshold. Store the one-time credential in the device relay secret store. Only the owning tenant can suspend or rotate it; rotation invalidates the old credential.
2. Create verified, serial-specific, dated employee enrolments. Re-enrolment closes the earlier period at the end of the previous day. Overlap, ambiguity and unknown IDs remain evidence for review; current biometric IDs never establish historical identity. Primary changes preserve previous periods. Publish stage-one coverage before evaluating attendance.
3. Device push uses `POST /device-attendance/iclock-ingest`, `X-Intake-Key`, optional `Idempotency-Key`, and `{sn, rows}`. Each row is tab-separated `deviceUserId`, timestamp, direction/status, verification mode, work code. Send 1–1000 rows, at most 4096 characters each. Status must be explicit (0–5). Timestamps must contain a valid date, hours, minutes and seconds. Ambiguous DST times require an offset.
4. A successful **202** acknowledges a durable receipt, not finished attendance. Retry a failed request with identical content and the same request key. Reusing a key with different content fails. Physical punch fingerprints suppress duplicates across adapters. Invalid rows are retained in the review inbox with their original text.
5. The worker evaluates employee/day windows using published configuration. It commits punch projection, attendance, configuration trace, audit and notification intent together. Failed attempts roll back and retry with exponential backoff; after eight failures an operator can explicitly retry. PostgreSQL transaction locks release on worker termination. Missing setup, identity conflicts and protected payroll periods remain in review.
6. HR reviews the inbox by state, opens the evidence trace, creates any missing dated enrolment, then resolves, retries or dismisses selected records with a reason. Review actions reject stale versions. Late enrolments are also reconciled automatically in bounded batches. Original evidence is immutable.
7. For historical files, download the template, preview CSV/XLSX, inspect before/after values and download the complete validation report. Include an approval reference and commit reason. All errors must be corrected before commit. Replacement of manually corrected rows requires the explicit preview option and attendance edit permission at commit. Each 100-row transaction advances a saved cursor; resume the same batch after an interrupted response. A changed attendance row requires a new preview. Imported decisions carry historical provenance and survive device replay.

## Deployment

- Apply `20261010100000_attendance_setup_releases`, then `20261010150000_attendance_capture`, using the normal migration process. Regenerate Prisma. The new tables require tenant RLS policies and the deferred receipt foreign key; do not create them manually without the migration.
- Pause the device relay during cutover, register devices, install credentials, confirm dated enrolments and published coverage, then enable receipt forwarding and the worker. The relay must accept HTTP 202 as success. Devices without registration are rejected; unresolvable identities are held, not guessed.
- The worker starts with the HR server. `ATTENDANCE_CAPTURE_WORKER_ENABLED=false` pauses processing while receipts remain available. Keep the existing outbox dispatcher enabled.
- Configure `ATTENDANCE_DEVICE_SN` before enabling the Python listener. Set `ATTENDANCE_SPOOL_DIR` to a persistent, access-restricted volume. Back up the spool with the database; do not delete queued files during restart. A local spool protects against database downtime, but loss of its host/disk still requires replay from the device. Bootstrap submissions are bounded to 500 punches.
- Each registered device initially permits only its owner. A shared terminal needs deployment-operator authorization of verified company UUIDs. Run `node scripts/configure-attendance-device.mjs --sn SERIAL --tenants OWNER_UUID,OTHER_UUID --operator OPERATOR --reason REASON` to preview, then repeat with `--apply-token TOKEN`. Tenant tools cannot grant cross-company access. Operator sync is always limited to the requesting tenant.
- Send authenticated `POST /device-attendance/heartbeat` with `{sn, deviceTime}` regularly. A gateway may prepend its service routing prefix. `deviceTime` must be sampled from the device clock, not a backlog punch. A heartbeat updates last contact and clock offset. More than 120 seconds of drift raises CLOCK_DRIFT; staleness takes precedence. The Python listener emits clock samples when its device connection supplies them.
- Do not run the former startup history importer. Startup no longer auto-applies historical files. Use the reviewed import workflow. Existing raw punches and attendance remain intact; records without a capture event retain their existing provenance. For legacy unassigned raw rows, preview `node scripts/resolve-orphan-punches.mjs --tenant OWNER_UUID --legacy`, then repeat with `--write` to create receipts. Continue with the returned `--after` cursor. Rows without original text require manual evidence review. This bridge cannot move a punch already assigned to another employee.

The evaluator continues using UTC-encoded civil wall coordinates (`punchedAt`). New capture also stores the actual instant (`occurredAt`), local timestamp and IANA timezone. Existing timestamps are never reinterpreted. The +/- one-day evaluation window protects adjacent overnight shifts; payroll protection conservatively includes those adjacent dates.

## Notifications and validation

The transactional outbox publishes `hr.attendance.capture_processed.v1` and `hr.attendance.device_health_changed.v1` to the existing HR event stream. Payloads include tenant-scoped IDs and health transitions. Notification-hub/gateway consumers must be configured for these new event names to deliver alerts; publication is not proof of delivery. The Capture screen polls while visible, so its inbox does not depend on those consumers. Legacy listener broadcasts contain receipt-level metadata only, without employee identity.

Before rollout, run the automated capture/import/attendance suites, Prisma validation and frontend build. In staging, apply migrations using the application role and verify tenant isolation, concurrent worker claims, crash recovery, duplicate delivery, cross-company shared-device routing, overnight capture, correction protection, import resumption and outbox delivery. Unit transaction fixtures do not validate PostgreSQL locking or RLS. No live migration or device hardware test was performed during development.

Device clock sampling uses the documented [pyzk get_time API](https://github.com/fananimi/pyzk#get-and-set-time). It never changes the device clock.
