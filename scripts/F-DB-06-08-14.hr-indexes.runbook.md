# HR Index Deployment (F-DB-06/F-DB-07/F-DB-08/F-DB-14)

`ARCH-01 §5.5` requires production indexes to be built concurrently after the
transactional Prisma migration phase. The SQL file intentionally contains no
transaction block and must use a direct PostgreSQL URL.

1. Run `npx prisma migrate deploy` normally.
2. Set `DATABASE_DIRECT_URL` to the direct PostgreSQL endpoint.
3. Run `npm run db:indexes:deploy` once per environment.
4. Re-run the command safely after interruption; every operation is idempotent.
5. Check for invalid interrupted builds with:

```sql
SELECT indexrelid::regclass, indisvalid, indisready
FROM pg_index
WHERE NOT indisvalid OR NOT indisready;
```

Do not put the concurrent SQL into a Prisma migration. For a fresh database,
replay the Prisma chain first and then run this deploy step. Development may use
Prisma's generated non-concurrent index migration instead, but that takes a
stronger table lock and must not be used against a busy production table.

The replacement indexes are created before overlaps are dropped. `CREATE INDEX
CONCURRENTLY` reduces writer blocking but performs extra table scans and I/O;
schedule it away from payroll/attendance peaks. The retained indexes add write
amplification to queue status transitions and high-volume attendance writes, in
exchange for bounded worker scans and tenant-qualified list/payroll reads.
